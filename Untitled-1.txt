# Задача: Разработка приветственного окна и локальной системы заметок для обратной связи

## 1. Общая концепция

Необходимо реализовать в приложении приветственное информационное окно, которое будет отображаться при первом запуске программы, а также отдельную систему заметок для обратной связи и сбора предложений по улучшению приложения.

Основная идея заключается в том, чтобы пользователь мог самостоятельно фиксировать обнаруженные проблемы, ошибки, пожелания, идеи новых функций и предложения по доработке существующего функционала.

Все заметки должны храниться в одном локальном TXT-файле. Пользователь должен иметь возможность создавать новые записи, просматривать ранее сохранённые заметки и редактировать их.

Система должна быть простой в использовании, надёжной и не требовать подключения к Интернету.

## 2. Приветственное окно при первом запуске

При первом запуске приложения необходимо показать отдельное информационное окно.

В нём должны присутствовать:

- Краткое описание назначения приложения.
- Небольшое приветствие пользователя.
- Информация о возможности оставлять заметки с предложениями по улучшению программы.
- Перечень возможных типов заметок:
  - Обнаруженные ошибки и баги.
  - Предложения по добавлению новых функций.
  - Идеи по улучшению существующего функционала.
  - Другие замечания и пожелания.

Предусмотреть кнопку закрытия или подтверждения ознакомления.

**Дополнительные требования:**

- Окно должно отображаться только при первом запуске приложения.
- Факт ознакомления необходимо сохранять локально, чтобы при последующих запусках окно повторно не появлялось.
- Предусмотреть возможность повторного открытия информационного окна через настройки или соответствующий раздел приложения, если это соответствует существующей архитектуре.

## 3. Система создания новых заметок

Необходимо реализовать отдельный интерфейс для создания заметок.

Пользователь должен иметь возможность добавить новую заметку, указав следующие данные:

1. **Название заметки** — краткое описание проблемы, идеи или предложения.
2. **Категория** — тип заметки:
   - Ошибка / баг.
   - Новая функция.
   - Улучшение существующего функционала.
   - Другое.
3. **Описание** — подробное изложение сути проблемы или предложения.

Примеры:

**Пример 1:**
- Название: Ошибка при запуске.
- Категория: Ошибка / баг.
- Описание: При запуске приложения иногда появляется ошибка...

**Пример 2:**
- Название: Добавить новую функцию.
- Категория: Новая функция.
- Описание: Предлагаю реализовать возможность...

Интерфейс должен быть интуитивно понятным и не требовать лишних действий.

## 4. Просмотр ранее созданных заметок

Необходимо предусмотреть отдельный раздел, в котором пользователь сможет просматривать все ранее сохранённые заметки.

**Основные возможности:**

- Отображение списка всех существующих заметок.
- Отображение названия каждой заметки.
- Отображение её категории.
- Отображение даты и времени создания.
- Возможность открыть любую заметку для просмотра полного содержимого.
- Удобная навигация между записями.

Заметки должны отображаться в порядке их создания, с сохранением последовательной нумерации.

Если заметок ещё нет, необходимо показать понятное сообщение об отсутствии записей и предложить создать первую заметку.

## 5. Редактирование ранее созданных заметок

Необходимо реализовать возможность редактирования любых ранее созданных заметок.

**Пользователь должен иметь возможность:**

- Изменять название заметки.
- Изменять её категорию.
- Редактировать основной текст описания.
- Сохранять внесённые изменения.
- Отменять редактирование без изменения исходной записи.

**Принцип работы:**

1. Пользователь открывает раздел заметок.
2. Выбирает необходимую запись из списка.
3. Открывает её для просмотра.
4. При необходимости переходит в режим редактирования.
5. Вносит необходимые изменения.
6. Подтверждает сохранение.

После сохранения изменения должны применяться к существующей записи в общем TXT-файле.

**Важные требования:**

- Редактирование не должно создавать новую заметку вместо изменения существующей.
- Нумерация заметок должна сохраняться.
- Дата первоначального создания должна оставаться неизменной.
- Дополнительно предусмотреть фиксацию даты и времени последнего изменения.
- Остальные заметки не должны изменяться при редактировании выбранной записи.
- При отмене редактирования исходное содержимое должно оставаться нетронутым.

## 6. Хранение заметок в одном TXT-файле

Все заметки необходимо хранить в одном общем текстовом файле формата `.txt`.

**Принцип работы:**

1. До создания первой заметки TXT-файл не создаётся.
2. При сохранении первой заметки приложение автоматически создаёт TXT-файл в заранее определённом локальном каталоге.
3. Все последующие заметки добавляются в этот же файл.
4. Каждая заметка должна иметь собственный визуально отделённый раздел.
5. При редактировании существующей заметки обновляется только соответствующая запись.
6. Новые заметки добавляются последовательно, не удаляя и не изменяя предыдущие записи.

**Рекомендуемый формат хранения:**

```text
========================================
ЗАМЕТКА №1
========================================

Название: Ошибка при запуске
Категория: Ошибка / баг
Дата создания: 07.11.2026 12:30
Последнее изменение: 07.11.2026 12:30

Описание:
При запуске приложения иногда появляется ошибка...

========================================
ЗАМЕТКА №2
========================================

Название: Добавить новую функцию
Категория: Новая функция
Дата создания: 07.11.2026 13:15
Последнее изменение: 08.11.2026 10:20

Описание:
Предлагаю добавить возможность...

========================================
```

Форматирование должно обеспечивать удобное чтение файла даже при большом количестве заметок.

**Дополнительные условия:**

- Использовать кодировку UTF-8.
- Обеспечить корректное сохранение кириллицы, специальных символов и переносов строк.
- Не создавать отдельный TXT-файл для каждой заметки.
- Не создавать дополнительные TXT-файлы при последующих запусках.
- Использовать один постоянный файл для всех записей.
- Обеспечить последовательную нумерацию заметок.

## 7. Надёжность и безопасность хранения данных

Особое внимание уделить сохранности пользовательских заметок.

Поскольку при редактировании отдельной записи может потребоваться обновление содержимого всего TXT-файла, необходимо реализовать безопасный механизм сохранения.

**Обязательные требования:**

- Перед изменением файла проверять возможность записи.
- Использовать безопасную перезапись через временный файл с последующей заменой оригинального.
- Не допускать потери ранее сохранённых заметок при ошибках записи.
- Обрабатывать ситуации отсутствия доступа к каталогу или файлу.
- При ошибке сохранения уведомлять пользователя и не сообщать об успешном выполнении операции.
- Не допускать создания пустых заметок.
- Проверять наличие названия и описания перед сохранением.
- При отмене редактирования не изменять исходную запись.
- Корректно обрабатывать неожиданные символы и переносы строк.

Если TXT-файл отсутствует, повреждён или не может быть прочитан, приложение должно корректно обработать ситуацию и уведомить пользователя, не перезаписывая потенциально восстанавливаемые данные.

## 8. Требования к интерфейсу

Новая функциональность должна соответствовать существующему визуальному стилю приложения.

Необходимо предусмотреть следующие элементы:

**Приветственное окно:**
- Краткая информация о приложении.
- Описание системы обратной связи.
- Кнопка подтверждения ознакомления.

**Раздел заметок:**
- Список ранее созданных записей.
- Кнопка создания новой заметки.
- Возможность открыть существующую запись.
- Возможность перейти к её редактированию.

**Форма создания и редактирования:**
- Поле названия.
- Выбор категории.
- Многострочное поле описания.
- Кнопка сохранения.
- Кнопка отмены.

**Уведомления:**
- Подтверждение успешного создания заметки.
- Подтверждение успешного изменения заметки.
- Понятные сообщения об ошибках.
- Предупреждение при попытке закрыть форму с несохранёнными изменениями.

Не перегружать интерфейс лишними элементами. Сохранить понятную навигацию и единый визуальный стиль.

## 9. Расположение и доступность TXT-файла

TXT-файл должен находиться в постоянном локальном каталоге, доступном приложению для чтения и записи.

Рекомендуется использовать пользовательский каталог данных приложения, а не директорию, в которой расположен исполняемый файл `.exe`.

Это необходимо для корректной работы программы при установке в защищённые системные директории Windows.

Расположение файла должно быть предсказуемым и стабильным между запусками приложения.

## 10. Ограничения реализации

Перед началом разработки необходимо изучить существующую архитектуру проекта и определить наиболее подходящий способ интеграции новой функциональности.

Обязательные ограничения:

- Не переписывать существующие компоненты без необходимости.
- Не нарушать работу текущего функционала.
- Не изменять существующую архитектуру проекта без объективной причины.
- По возможности использовать уже существующие механизмы хранения настроек.
- Не добавлять сторонние зависимости без необходимости.
- Соблюдать принятый в проекте стиль программирования и архитектурные принципы.
- Не удалять и не изменять существующие пользовательские данные.

Если в процессе реализации обнаружатся архитектурные ограничения, сначала определить оптимальное решение, а не вносить необоснованные изменения.

## 11. Критерии готовности

Функциональность считается полностью реализованной, если выполнены все следующие условия:

1. При первом запуске появляется приветственное окно.
2. При последующих запусках оно не появляется повторно.
3. Пользователь может создать новую заметку с названием, категорией и описанием.
4. При сохранении первой заметки автоматически создаётся один TXT-файл.
5. Все последующие заметки сохраняются в этот же файл.
6. Каждая запись имеет отдельный визуально выделенный раздел.
7. Пользователь может просматривать список всех сохранённых заметок.
8. Пользователь может открывать отдельные заметки.
9. Пользователь может редактировать название, категорию и описание существующей заметки.
10. Изменения сохраняются в исходной записи, без создания дубликата.
11. Дата первоначального создания не изменяется при редактировании.
12. Дата последнего изменения обновляется.
13. Остальные заметки остаются нетронутыми.
14. Нумерация записей сохраняется.
15. Кириллица, специальные символы и переносы строк обрабатываются корректно.
16. Ошибки чтения и записи обрабатываются безопасно.
17. При сбое сохранения ранее существующие данные не теряются.
18. Новая функциональность не нарушает работу остальных компонентов приложения.

## 12. Порядок выполнения работы

Перед внесением изменений:

1. Изучить текущую структуру проекта.
2. Определить место интеграции приветственного окна и системы заметок.
3. Проверить существующие механизмы хранения локальных настроек.
4. Составить краткий план реализации.
5. Определить способ безопасного чтения, добавления и редактирования записей в TXT-файле.

После этого приступить к реализации.

По завершении:
- Проверить работу приветственного окна при первом и последующих запусках.
- Проверить создание нескольких заметок.
- Проверить редактирование разных записей.
- Проверить сохранение кириллицы и многострочного текста.
- Проверить поведение при отсутствии файла и ошибках доступа.
- Убедиться, что предыдущие заметки не повреждаются и не теряются.
- Проверить отсутствие регрессий в существующем функционале.

## Ожидаемый результат

Полностью интегрированная в приложение система обратной связи, включающая приветственное окно и удобный раздел заметок.

Пользователь должен иметь возможность в любой момент создавать новые заметки, просматривать ранее сохранённые записи и редактировать их.

Все записи хранятся в одном локальном TXT-файле с понятной структурой и последовательной нумерацией. Система должна работать автономно, надёжно и не зависеть от подключения к Интернету.
